# 2026-11-08 · F-100 In-app chat (host ↔ vendor)

- **Feature:** F-100 In-app Chat — host-vendor conversations (`8619d25c-e294-45f9-a84a-a6332af4d650`,
  must, stage `structure`). The proposal was approved and assigned on 2026-11-06; the context
  package served for it was version 7, compiled 2026-11-06 and flagged `stale`.
- **Feature description (Sage 7):** _"Hosts and vendors can hold in-app conversations before a quote
  exists, scoped to one Host house and one Vendor house, with the messages visible only to the two
  sides."_
- **Owner instruction (2026-11-08):** _"The chat or conversation should flow like whatsapp UI with all
  relevant tools for sharing documents."_ The thread was therefore rebuilt as a messaging-style
  conversation, and document sharing was added to it.

## What the feature delivers

1. **One private conversation per house pair.** `public.conversations` carries the Host house and the
   Vendor house, with composite foreign keys to `public.houses (id, kind)` so a conversation cannot
   point at a third party or at the wrong kind of house. A unique constraint on
   `(host_house_id, vendor_house_id)` keeps one thread per pair.
2. **Only the two sides may read or write.** RLS is enabled **and forced** on `conversations` and
   `messages`; the policies admit a member of either house whose membership carries the `chat`
   capability (`app_private.member_can`, the F-14 mirror of the F-78 role matrix). Vendor staff need
   the grant their owner gave them; host houses stay owner-only.
3. **Messages are append-only.** `app_private.forbid_change()` blocks updates, deletes and truncates.
4. **The browser never writes a table.** Every write goes through a `security definer` function
   (`start_conversation`, `send_message`, `send_document`); write grants are revoked from
   `anon`/`authenticated`.
5. **Documents can be shared in the thread.** A file is uploaded to a private storage bucket under
   the conversation's own path, recorded in `message_attachments`, and delivered as a message.

## The conversation UI

The thread was rebuilt as a messaging surface rather than a form:

- a header with the counterparty, an avatar and the privacy line ("only you and X can read this");
- bubbles that follow the familiar convention — the caller's own messages right and dark, the
  other side's left and white — with a day separator between groups and a timestamp inside each
  bubble;
- a composer pinned to the bottom that grows with the message, sends on Enter (Shift+Enter for a
  new line) and keeps what was typed when a send fails;
- the house's conversations as a list of rows with the counterparty, the time, the last message and
  the message count;
- loading, empty and error states everywhere, with a retry that keeps the user's place.

## Sharing documents

- **Two tools in the composer:** "Document" and "Photo", offering only the types the bucket allows
  (`application/pdf`, Word, Excel, PowerPoint, plain text, CSV, JPEG, PNG, WebP, HEIC). SVG is not
  offered and is refused by the server, so a shared file cannot carry script.
- **The file is checked twice.** The route rejects an unknown type or a file over 10 MB; the bucket
  enforces the same limit and the same type list; and `public.send_document` checks the type, the
  size and the path again in the database, so a file that reached the bucket another way still
  cannot be attached.
- **The file belongs to the conversation.** It is stored under
  `conversations/<conversation id>/<file id><name>`, and `send_document` refuses a path that names a
  different conversation. `message_attachments` carries a composite foreign key on
  `(message_id, conversation_id)`, so an attachment cannot claim a conversation its message is not in.
- **The bytes stay private.** The bucket `chat-attachments` is not public; the storage policies admit
  only a participant of the conversation the path names; and the download link is a five-minute
  signed URL minted with the caller's own token.
- **A document may travel without a caption.** The message body check was relaxed to 0..4000
  characters for that reason; a message without a caption is only created together with an
  attachment.

- `src/routes/api/chats/$id/attachments.ts` — `POST /chats/:id/attachments`.

- `src/pages/HousePage.tsx` — the "Enquiries" page of both houses now mounts the chat panel.

Every route forwards the caller's own token to PostgREST or to the storage API, so the database
decides what the caller may do. No service-role key is read on these paths, and a secret key is
refused rather than used: it would answer as the server instead of as the caller.

## Not done / limits

- **Neither migration has been applied to the hosted database.** There is no database password or
  connection string in this repository, so the migration files were written and reviewed but not run.
- **Malware scanning is absent.** No scanning provider has been approved (AGENTS.md forbids adding
  one), so a shared file is type- and size-checked but never scanned. The bucket is private and only
  the two parties can reach the file.
- **The thread does not poll.** New messages appear when the conversation is reloaded or after a
  send. Realtime is not wired up.
- **A shared file is not deleted with the conversation.** F-39 (record retention) has not been
  built, so the bytes stay in the bucket until then.
- **One attachment per message.** A message carries one document; a second file needs a second
  message.
- The conversation list shows no unread badge and no last-seen marker: the schema does not carry
  them yet.
