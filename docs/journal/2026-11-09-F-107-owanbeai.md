## The gate is open (owner answer, 2026-11-10)

The feature was built with the zero-retention gate **closed**, because the contract did not exist
yet. The owner then answered the question this build raised (Sage 7 question `3e793b14`,
2026-11-10): *"Lovable has ZDR and gpt also has ZDR in place so this is okay to function now."*

1. **The confirmation is recorded, not assumed.**
   `supabase/migrations/20261110203000_f107_open_zdr_gate.sql` writes the owner's confirmation into
   `app_private.ai_settings`: the provider (the Lovable AI Gateway, OpenAI gpt, zero data
   retention), a reference back to the answer (`owner confirmation 2026-11-10, Sage 7 question
   3e793b14`), and the moment it was confirmed. The table stays revoked from every application
   role, so **no application path can open or close the gate** — the owner can, and the migration
   is that act. The migration carries the statement that closes it again.
2. **Nothing about the trail changed.** The gate decides whether a payment trail may be read at
   all; opening it does not widen the trail. The log is still minimised in the database, every read
   is still a sensitive read with a purpose, and the `ai_investigation` grant still carries no fund
   authority. OwanbeAI can read and open a case; it cannot allocate, refund, settle, freeze,
   unfreeze, complete or release.
3. **The suite proves both states from a known one.** It used to assert that the gate *starts*
   closed, which would now be false. It closes the gate as the owner first, proves the refusals,
   proves that no application role can change it in either direction, and then opens it with the
   same values the migration records.
4. **The application needed no change.** The gate was always the database's: `ai_payment_log`
   raises `zdr_contract_required` while it is closed, and the app never calls a model without a
   trail the database handed it. Every "closed" word in the app is conditional on the database's
   answer, so the panel appears by itself once the gate is open and the copy stays true either way.
5. **F-65 stays open.** This records that the platform's provider already holds a zero-data-
   retention agreement. F-65 is about the contract itself — who signs it, whether the platform
   should *verify* it rather than record it, and what the model vendor owes in writing.

## What the feature delivers

1. **One AI provider for the whole platform.** `src/lib/ai/provider.server.ts` holds the model, the
   gateway and the rules that guard a call. A request marked **sensitive** is refused unless a
   zero-retention contract is confirmed — the database decides that, nothing in the app assumes it.
   Every call sets `store: false`, so the provider is never asked to keep the exchange.
2. **One AI label and one report control.** `src/features/ai/AiDisclosure.tsx` holds the badge that
   says the words came from a model and the form that lets the reader say the answer was wrong.
   The planner (F-101) and the vendor copy studio now use them instead of their own copies, so
   there is one disclosure wording and one report route for every surface.
3. **OwanbeAI reads a payment trail and opens a case.** The staff panel on a booking's payments
   panel asks a question, the model reads the trail, and the answer is one of three findings:
   nothing wrong, a person must look, or a case was opened. OwanbeAI never moves money.
4. **The trail it reads is minimised in the database.** `public.ai_payment_log` returns money and
   state — totals, what was paid, what is held, what was released, what was refunded, timestamps,
   counts. No party name, no email address, no provider reference, no payload. The prompt builder
   never adds them either, and never puts a booking id or an event id in front of the model.
5. **The money guarantee is the database's, not the app's.** The `ai_investigation` grant carries no
   fund authority. `supabase/tests/f107_owanbe_ai.test.sql` section 7 proves the AI path cannot
   allocate, refund, settle, freeze, unfreeze, complete or release: it calls
   `ai_payment_log`, `ai_payment_event_log`, `log_ai_interaction` and `open_ai_case`, and nothing
   else exists on that path.
6. **The gate is closed, and it says so.** `app_private.ai_settings` holds the contract record and
   `app_private.ai_zdr_confirmed()` reads it. No application role can write to that table, so the
   gate can only be opened by the owner. While it is closed, `ai_payment_log` raises
   `zdr_contract_required`, the route answers `503 locked`, and the panel does not appear at all.

## The rules that live in the database

- `public.ai_investigation_status()` — one read that says whether the zero-retention contract is
  confirmed, whether this caller holds the grant, and therefore whether OwanbeAI may be shown.
- `public.ai_payment_log(p_booking, p_purpose)` — the minimised payment trail. Refused without the
  grant (42501) and refused while the contract is unconfirmed (22023). Every read is a **sensitive
  read** and is audited by `app_private.log_sensitive_read`.
- `public.ai_payment_event_log(p_booking, p_purpose)` — the provider's own events: type, outcome,
  amount, currency, time. The payload and the reference are not returned, so a partner token cannot
  be read back out of the log.
- `public.log_ai_interaction(...)` — the answer is logged against the caller, so it can be reported
  and so a case points back at the investigation that found it.
- `public.open_ai_case(...)` — the AI's own case, with its subject, reason and priority. It opens
  one; it does not decide anything about it.
- `public.report_ai_interaction(...)` — one report per answer. The database refuses a second one
  rather than merging it.
- `public.cases` and `public.ai_interactions` have RLS **enabled and forced**, no policies and
  `revoke all` from `public`, `anon` and `authenticated`: nobody selects them, and the app's own
  routes forward the caller's token so the database decides.
- `app_private.keep_payment_event_booking()` — a narrow repair: F-102's write-back cleared the
  booking on a failed payment event, so the trail back to the booking was lost. The trigger puts
  the booking back when the outcome was never decided, and touches nothing else.

- **One flake, found and fixed.** On the first whole-suite run the planner's "reports an answer"
  test failed: the report form opened and closed again in the same breath. The cause was the shared
  `AiReportControl`, which reset its own state from a `useEffect` on `[interactionId]`. That effect
  also fires **on mount**, so a click that landed before the mount effect had flushed was wiped by
  it — a race a person can hit by clicking "Report this answer" the instant the answer appears. The
  reset now happens while rendering, when the interaction id actually changes, and there is no
  effect to fire on mount. The window could not be reproduced deterministically in jsdom
  (`flushSync` commits and flushes the passive effects together, and Testing Library's `act`
  flushes them before the handler runs), so the guard is an invariant test — the form stays open,
  and what was typed stays typed, while the answer on screen does not change — rather than a
  reproduction of the timing.

## Not done / limits

- **The migration has not been applied to any database.** There is no database password or
  connection string in this repository, so the file was written and reviewed but never run.
- **The SQL suite has never been executed.** Every database-side claim in this entry is a claim
  about the SQL, not a test result.
- **The zero-retention gate is open, but it was opened by a confirmation, not by a document.** The
  owner confirmed on 2026-11-10 that the platform's provider (Lovable AI Gateway, OpenAI gpt) holds
  a zero-data-retention agreement; `supabase/migrations/20261110203000_f107_open_zdr_gate.sql`
  records that confirmation in `app_private.ai_settings`. No application role can write that row,
  and no signed contract is stored in the platform, so what the platform can prove is the owner's
  answer, not the contract itself. The route still refuses if the row is missing or closed.
- **There is no separate staff surface.** The panel lives in the Host house, so a grant holder must
  also be a member of that host house to reach it. A platform staffer who is not in the house sees
  nothing. A dedicated staff console is a later feature.
- **The case queue is a table, not a workflow.** `public.cases` holds what the AI opened and who
  opened it. Nothing yet assigns cases, escalates them or closes them; F-16 Disputes & Refunds
  Console extends the table.
- **The model is one model for every surface** (`openai/gpt-6-astra`), and the answer is a
  statement or a case. It is not a decision-maker and it has no tool that could move money.
- **The report control is one report per answer.** The database refuses a second report on the
  same interaction rather than merging it, so a reader who wants to add something must wait for the
  first report to be handled.
