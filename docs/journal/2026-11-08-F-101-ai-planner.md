## Owner decisions taken before the build (2026-11-08)

1. **Plan approval** — approve the plan as described: a grounded planner that cites published
   vendors only, labels what it cannot confirm, carries an AI disclosure and a report control on
   every output, logs every interaction, and wires the three lines the tracker names.
2. **What the AI log keeps** — the brief and the plan summary: the event type, city, guest count,
   budget, the host's brief, and the generated option titles/summaries and cited vendors. No guest
   data, no contact details, no payment identifiers.
3. **Prices** — only the vendor's own price note. A price is shown when the vendor published it
   themselves; otherwise it reads "Price unknown — request a quote". The planner never invents a
   number.

## What the feature delivers

1. **The planner answers with published vendor data only.** The server reads the published vendor
   profiles (`public_vendor_profiles`) with the caller's own token and passes only those facts, plus
   what the host told us, to the model. A vendor the model names that no published profile backs is
   dropped from the answer, and the count of what was dropped is shown to the host.
2. **Prices are the vendor's, or they are unknown.** A price is read from the vendor's own price
   note and shown in the vendor's own words. If the note carries no readable amount, states a price
   per guest, or is written for a different number of guests, the answer reads "Price unknown —
   request a quote" and the budget fit stays unknown. A price the model wrote into its prose is
   removed before the answer is shown.
3. **Availability is always unknown.** The platform holds no per-date vendor calendar, so every
   vendor carries "Availability unknown — ask the vendor", and a claim of availability in the
   model's prose is softened to "may be available".
4. **The disclosure is on every output.** "AI-generated plan" sits on the form, on the answer and on
   each option.
5. **Every answer can be reported.** The host reports one answer under one category, with an
   optional note. The report is recorded against the interaction, once.
6. **Every interaction is logged, including the failures.** A row is written per generation with the
   host's brief, the plan as shown and the status; a generation that failed is logged as `error`,
   so the trail stays honest.

## The rules that live in the database

- `public.ai_planner_interactions` — one row per generation, RLS enabled **and forced**, the host
  reads their own rows and nobody writes the table directly.
- `public.log_ai_planner_interaction(...)` — the only way in. It refuses a caller who is not in a
  Host house (`forbidden: planner`), validates every field, enforces one generation per 30 seconds
  (`rate_limited: planner`) and resolves the vendor names in the log from the published profiles, so
  a caller cannot record a business that does not exist. The prose it keeps is what the host saw.
- `public.report_ai_planner_response(...)` — one report per answer; a second report is refused
  (`already_reported`) rather than merged.
- `public.ai_planner_cooldown_seconds()` — the server asks before it spends anything on the model;
  the log function checks again, so two requests that race cannot both be recorded.
- `public.my_ai_planner_interactions()` — the caller's own last 20 rows.

## The rules that live in the app

The database cannot check whether a price is a real price, so that check is in code
(`src/features/planner/contracts.ts`):

- `parsePriceNote` reads the amount out of the vendor's own note, and refuses to read one that is
  per unit or written for another number of guests.
- `budgetFitFor` compares only within the same currency; a price in another currency stays unknown
  rather than being converted at a rate the platform does not have.
- `groundPlan` drops a vendor with no published profile, replaces the model's price claims with
  "a price to confirm", forces the unknown-availability label and counts what it removed.
- The model is instructed (and the prompt is the only place it is told anything) that it may name
  only the vendors it was given, and may state neither a price nor an availability.

## Not done / limits

- **The migration has not been applied to the hosted database.** There is no database password or
  connection string in this repository, so the file was written and reviewed but not run.
- **The plan is never signed.** The model is instructed not to sign; nothing checks it afterwards,
  because a signature check on generated prose proves little.
- **The plan is not persisted as a document.** Only the summary is logged; the host cannot reopen an
  old plan, only the last 20 interactions are listed and the panel does not show them yet.
- **The budget fit is coarse.** It compares one price with the whole budget, so a vendor who quotes
  per guest, or for a different number of guests, is left unknown rather than misjudged.
- **The 30-second cooldown is a decision the owner has not confirmed.** It is a constant in the
  migration and in the app (`PLANNER_COOLDOWN_SECONDS`); changing it means changing both.
- **Zero data retention (F-65) is not built.** The gateway call sets `store: false`, but the
  provider's own retention terms are the owner's responsibility, and F-65 must still be built and
  confirmed before the planner sends anything a host would mind being kept.
- **The planner answers only for published vendors.** With no published profile there is nothing to
  build on, and the panel says so instead of inventing one.
