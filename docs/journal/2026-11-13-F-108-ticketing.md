# 2026-11-13 · F-108 Ticketing system

## What was missing

F-108 is the ticket-to-the-door path: a host issues an invitation link, a guest claims it and
gets a card, and a door device admits the card and records the admission. Nothing of that
existed. The repository had guest lists (F-40) and their privacy controls, but no invitation, no
claim, no admission and no scanner.

The owner approved the shape of it before the work started:

- *"Approve, and include the scanner app"* — the door device is part of the feature, not a
  later addition.
- Phone binding: *"Bind as typed, hashed (Recommended)"* — the phone a guest gives is stored only
  as a hash, and it binds the claim so the same person cannot take a second place on the same
  link.
- Scanner identity: *"Host-issued scanner grant (Recommended)"* — the person holding the door
  device is named by the host, on a device-bound grant the host can take back.
- QR/NFC: *"Build the Expo app too"*, and *"I believe we are also building a mobile version of
  the Owanbe, this is where the QR NFC will be integrated."*

Sage 7 confirmed the acceptance criteria: *"Claim binds invitation/phone without requiring full
account"*; *"Atomic claims allow one person or two for couple links"*; *"QR/NFC admission
supports offline scanner cache"*; *"Only host can invalidate or reissue invitation tokens"*.
The wiring lines were `table invitations`, `api POST /invitations/claim`, `route /invite/:token`
and `fn claimInvitation`.

## What was delivered

### The database — `supabase/migrations/20261113150000_f108_ticketing.sql`

Five tables, RLS **enabled and forced** on each, `revoke all … from public, anon, authenticated`
and `grant all … to service_role`: `invitations`, `invite_claims`, `admissions`,
`scanner_grants`, `checkins`. Nothing is reachable from the client directly; every read and
every write goes through a `security definer` function with `set search_path = ''`.

The decisions that mattered:

- **The token is a single secret.** `create_invitation` mints it and returns it **once**; the
  platform keeps only `sha256(token)`. `host_invitations` gives the host a *fingerprint* of the
  link, never the link. A lost link is reissued, not recovered.
- **A claim is atomic.** `claim_invitation` hashes the token, locks the invitation row
  (`for update`), counts the active claims **under that lock**, and inserts a claim with a slot.
  `unique (invitation_id, slot)` and a partial `unique (invitation_id, phone_reference) where
  status = 'active'` are the database's own guarantees. A couple's link admits two people and
  never three, and the same phone cannot take a second place.
- **The guest needs no account.** `claim_invitation` and `my_claimed_card` are granted to
  `anon`. The web route refuses a `sb_secret_` key and calls the functions with the publishable
  key only.
- **The phone is stored as a hash.** `phone_reference` is a hash, not a number, so the platform
  cannot read back who came to the door.
- **Admission is derived, not stored.** The credential is
  `sha256('owanbe-admission:' || guest_session)`. The guest's card carries it; the platform
  stores only `sha256(credential)`; `my_claimed_card` recomputes it from the session.
- **Only the host can invalidate or reissue.** Every host write passes
  `app_private.require_list_host(p_list)` (F-40's guard). `revoke_invitation` and
  `reissue_invitation` both take the row's `version`, so a stale screen is refused with
  `stale_version` instead of overwriting a newer change.
- **The door device is named, bounded and revocable.** `issue_scanner_grant` binds a grant to a
  `device_id`, a `grantee` and an expiry; `revoke_scanner_grant` takes it back.
  `public.grantee_for_list(list, email)` resolves the email to a **verified, active** person on
  the platform — an unknown, unverified or suspended address raises `grantee_not_found`, a
  malformed one raises `invalid_email`.
- **An offline admission is visible as such.** `record_checkin` takes a `mode`: `online` or
  `queued_offline`. A check-in made while the network was down is reconciled later and is not
  counted twice.

### The web app — `src/features/tickets/`

- `contracts.ts` — the shapes, the statuses, the copy and the validation schemas at the trust
  boundary.
- `api.ts` — the host-side boundary. It forwards the caller's own session and explains the
  refusal; it grants nothing itself. `classifyTicketError` turns the database's refusal into a
  code the interface can speak.
- `claim.ts` / `claim.server.ts` / `InviteClaim.tsx` — the guest's path: `/invite/:token`,
  `POST /api/invitations/claim`, `POST /api/invitations/card`. The route
  `src/routes/_public/invite.$token.tsx` uses the publishable key only.
- `scanner.ts` — the rules the door device shares with the phone (hash the credential, check
  the cache, queue when offline).
- `pairing.ts` — the pairing code format, shared by the web and the phone so there is one
  definition of the code.
- `InvitationsPanel.tsx` — the host's side: issue, reissue, revoke, hand the door device to a
  named person, and read the record the door leaves behind. The token is shown once, with a copy
  button.

### The phone — `mobile/` (Expo SDK 58, React Native 0.88)

A separate npm project (its own `package.json`, `app.json`, `metro.config.js` watching the repo
root so the app can import `src/features/tickets/scanner.ts` and `pairing.ts`).

- **My card** — claim a link from a shared URL, then read the card back, show it as a QR, copy
  it, or **write it to an NFC tag**.
- **The door** — pair with a grant (paste the code or scan it), scan a QR or read an NFC tag,
  admit, and see the check-in record.
- **Offline** — the scanner caches **hashes**, never a credential; a scan is hashed locally with
  `expo-crypto` and compared with the cache; a check-in made offline is queued and reconciled
  when the network returns.
- Auth is Auth0's authorization-code flow with PKCE, so there is no client secret on the
  device; long secrets are chunked into SecureStore.

## Decisions taken (owner-approved, recorded here)

1. **QR/NFC and offline reconciled with "store only hashes".** The QR carries the raw credential
   (that is what a ticket is), the scanner's cache carries `sha256(credential)`, and the device
   hashes locally before comparing. The platform stores only hashes either way, and
   `record_checkin`'s behaviour is unchanged.
2. **A host-issued scanner grant, not a new role.** The door operator's authority is a grant
   the host names, bounds and revokes, so F-78's capability matrix is untouched.
3. **No account for the guest.** The claim binds invitation and phone; it does not require an
   account.
4. **The pairing code avoids a new web dependency.** The host copies
   `owanbe://pair?grant=…&device=…&expires=…`; the door app can paste it **or** scan it. The
   format lives in one shared module.

## The owner's review, and what changed (2026-11-13, later the same day)

The owner reviewed the work and raised four points before merging. All four are answered here.

### 1. The held-back F-46 commits are not on this branch

The branch that was first pushed carried `956aa20` and `2b24ca3` — the F-46 handover fix, which is
held back on purpose. F-108 now lives on **`feat/F-108-ticketing-clean`**, cut from `origin/develop`
(`88bc3d8`), carrying only:

| Commit | What it is |
|---|---|
| `04575d7` | the F-108 build |
| `84e4100` | the memory bank |
| `e359dfe` | the memory bank (Sage 7 report and the open question) |

Neither `956aa20` nor `2b24ca3` is an ancestor of that branch, and the diff over the three F-46
files between `88bc3d8` and the branch head is empty.

### 2. The migration is rerun-safe

`supabase/migrations/20261113150000_f108_ticketing.sql` now applies more than once:

- tables are created `if not exists`,
- indexes are created `if not exists`,
- functions are **replaced** (`create or replace function`), not re-created,
- each trigger is dropped before it is created again.

A run that stopped halfway can therefore be re-run without a reset. `node
scripts/sql-shape-check.mjs` reports shape OK for the migration and for `f108_ticketing.test.sql`.

**What is still not proven is the execution.** This machine has no PostgreSQL 16 binaries and
Docker does not run here, and the Supabase MCP answers every call with an error, so the only place
the F-108 SQL can actually run is the `database` job of `.github/workflows/verify.yml`
(`bash supabase/tests/run-local.sh`). That job applies every migration and then every SQL suite in
a throwaway cluster. It triggers on a pull request into `main`; this branch is cut from `develop`,
so **the workflow does not run for it unless `develop` is added to the workflow's `pull_request`
branches** — a one-line change to `.github/workflows/verify.yml` that is left for the owner, since
CI configuration is theirs to change.

### 3. Q19 is answered: the offline cache is bounded by the door window

The decision is `docs/decisions/f108-offline-cache-window.md`; `docs/open-questions.md` Q19 is
marked answered. In short:

- The cache is bounded by the **door window** — the grant's own expiry, which the host sets. **No
  new threshold was invented.**
- The rules live in `src/features/tickets/scanner.ts`, shared by the phone and the tests:
  - `ScannerCache` carries the entries **and** the moment the platform gave them (`synced_at`);
  - `doorSyncState` says `ready`, `never_synced`, `empty` or `window_closed`;
  - `verifyAgainstCache` answers **`needs_sync`** — admitting nobody — when the cache was never
    fetched from the platform or the window behind it has closed.
- The door has **one** reconciliation action, **sync the door**: it sends the waiting check-ins and
  fetches the guest list again, in that order. There is no separate "refresh the list" and "send
  the queue", because a device that did one without the other would keep a guest list the platform
  does not agree with.
- The phone keeps the moment in SecureStore, and the door screen says when it is out of step.

The residual exposure is written down rather than hidden: while the device is dark it cannot see a
revocation, so the window is the bound on that exposure.

### 4. QR is the way in; NFC is an optional fast track

The camera path works on every phone, iOS and mid-range Android, with nothing but the app. NFC is
optional: writing a tag is **Android only**, and reading one needs a **development build**. The app
now says so — the guest's card reads *"Show this at the door — the camera reads it on any phone"*,
the door's button is a *fast track*, and `mobile/README.md` has a "QR first, NFC second" section.

## What is **not** proven

- **The migration has never been applied to a database and `f108_ticketing.test.sql` has never
  been executed.** This machine has no PostgreSQL 16 binaries and Docker does not work here
  (owner's instruction, 2026-11-08). The suite will first run in the `database` job of
  `.github/workflows/verify.yml`. The database side of F-108 is therefore **unverified**.
- **The Expo app has never been installed or run.** The npm registry is unreachable from this
  machine, so `mobile/` is code only, and its versions were read from the registry metadata
  rather than from an install. It also needs a **development build** — Expo Go cannot load
  `react-native-nfc-manager` — and writing an NFC tag is Android-only.
- **The NFC path is written against the v4 API of `react-native-nfc-manager`** (read from that
  package's own v4.2.0 documentation), but it has never run on a device.
- **The offline reconciliation is written, not exercised.** No device has queued a check-in.
- **`mobile/` has no `node_modules`**, so the phone app's own TypeScript project could not be
  type-checked here. The shared `src/features/tickets/scanner.ts` it imports **was** type-checked
  and linted, and it is the file the new rules live in.
