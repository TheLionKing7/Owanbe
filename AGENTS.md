## How agents use Sage 7 (10 tools)
Sage 7 MCP never edits code, dispatches builds or marks a feature built. Its only writes are reports to the owner's inbox (report_question, report_decision); without MCP, write open questions and decisions in docs/journal/ and docs/decisions/ and they are picked up on push. This workflow applies even when MCP is not connected. The tools are list_projects, get_next_task, get_feature_spec, get_context_markdown, get_context_package, get_context_status, report_question, report_decision, report_progress, get_answers.

- Read AGENTS.md and the blueprint/ documents in the repository first. They survive when MCP is not connected.
- Call list_projects when you need the project ID. When the owner asks you to start work, call get_next_task once for the feature to build.
- Call get_feature_spec for that feature, and get_context_markdown or get_context_package when you need the full context.
- Ask the user to approve a plan before writing code. Use get_context_status with the last version you read before refreshing.
- Build in stage order, like a building: Foundation, then Structure (shared engines, data and services), then Rooms (features people use), then Finishes. Only build the task get_next_task returns; work built ahead of its stage or prerequisites is held and doesn't count. If a feature needs something that isn't built, say so with report_question naming the feature code.
- Build one feature per branch. Include its feature ID in every commit message, for example feat(F-123): ...
- When a feature is done, call report_progress with its feature ID and commits. It shows as awaiting audit; audit evidence decides what is built, commits are only build evidence. Then stop and tell the owner: don't pull or start another feature until they say so.
- When the spec doesn't answer something, call report_question (blocking=true if you can't continue) with plain_language the owner can follow without technical knowledge; report decisions you make with report_decision. Never decide or build a feature whose blocking question you asked is still unanswered. Call get_answers at the start of each session.

## Golden rules

- Treat the feature map as the scope source of truth; preserve its must/should/could priorities and dependencies.
- Read the PRD, architecture, and relevant decisions before implementation. Flag contradictions rather than silently choosing a rule.
- Implement only the requested feature and necessary dependencies. Avoid speculative features and unrelated refactoring.
- Enforce business rules on the server and in the database; never rely on hidden buttons or client-side checks.
- Target **OWASP ASVS Level 3**. Map applicable requirements to implementation and verification evidence; do not claim compliance from a checklist alone.
- Preserve Host/Vendor house separation across queries, routes, caches, notifications, search, storage, and live subscriptions.
- Fail closed for authorization, money movement, verification, and sensitive-data access.
- Never invent financial thresholds, legal permissions, provider capabilities, or unresolved product policies.
- Keep changes small, reviewable, reversible, and traceable to an approved feature ID.
- Include the feature ID in **every commit message**:
  - Single project: `feat(F-123): enforce quote revision expiry`
  - Multiple Sage 7 projects: `feat(<project-slug>/F-123): enforce quote revision expiry`
  - Apply the same scope convention to `fix`, `test`, `docs`, and other commit types.
- Request the canonical feature ID when missing; do not assign invented IDs to feature-map entries.

## How to approach a task

1. **Read first**
   - Read the PRD, architecture, `design_system.md`, this file, and applicable owner decisions.
   - Inspect existing code, migrations, access policies, tests, and deployment configuration.
   - If required documents are missing, ask for them; do not substitute assumptions.

2. **Plan**
   - Identify the feature ID, acceptance criteria, dependencies, affected roles, and workspace boundaries.
   - Outline UI states, data changes, authorization, background work, and verification.
   - Identify migrations, rollback constraints, external integrations, and unanswered questions.

3. **Implement in small steps**
   - Prefer a narrow end-to-end slice over broad scaffolding.
   - Reuse existing components and domain services.
   - Add database constraints and access policies alongside new tables.
   - Separate refactoring from behavior changes wherever practical.

4. **Verify**
   - Run repository-approved checks and targeted tests, then relevant regression tests.
   - Exercise unauthorized access, concurrency, retries, outages, and boundary timestamps.
   - Review diffs for secrets, dependency changes, hardcoded styles, and unrelated edits.

5. **Report**
   - Summarize changes, checks run, migration implications, and remaining risks.
   - Distinguish verified behavior from untested behavior.
   - Log blocked acceptance criteria; never describe placeholders as completed integrations.

## Data & security rules

### Access and identity

- Enable row-level security on exposed Supabase tables and Storage objects; default to deny.
- Derive authorization from verified identity and current membership, never client-supplied user IDs or house IDs.
- Use Auth0 as the designated authentication authority. Document and verify its integration with Supabase identity and RLS before shipping; do not create a competing Supabase login system.
- Enforce vendor capabilities at the API and database layers. Allow only vendor owners to manage payout details; do not permit host delegation.
- Revoke removed team members immediately, including live sessions, subscriptions, cached authorization, and active operations.
- Allow vendor owners to inspect team conversations.
- Restrict support to permitted chat/case data, excluding payment details. Scope event managers to assigned events and approved fields.
- Log sensitive reads and changes without copying sensitive payloads into logs.
- Separate support-only no-show evidence from host-visible progress and authorized vendor evidence submission.
- Protect guest contact details regardless of public/shared list settings; enforce revocation immediately.

### Secrets, input, and files

- Keep secrets and privileged credentials server-side. Treat Vite and Expo client configuration as public.
- Validate request bodies, query parameters, uploads, provider responses, and webhook payloads server-side.
- Verify webhook signatures and reject replayed or duplicate events safely.
- Rate-limit authentication/recovery, invite claims, messages, uploads, AI requests, search, and financial endpoints.
- Enforce recovery attempt limits and OTP expiry server-side; never display or log trusted-partner nicknames.
- Quarantine uploads until approved file-type and malware checks complete. Do not publish unscanned files.
- Restrict private documents through Storage policies and short-lived authorized access.
- Redact identity, health, biometric, financial, and secret data from Sentry, analytics-like events, job logs, and AI traces.

### Financial integrity and scheduling

- Store only partner tokens/references, balances, and transaction records; never store raw card or bank-account credentials.
- Maintain an auditable, append-only financial ledger. Reconcile provider events before declaring payment success.
- Use transactional constraints for date races and invite claim limits; never use client-side “check then write.”
- Make first-confirmed-payment selection atomic; schedule idempotent losing-payment refunds and reversal receipts.
- Make payment, refund, release, and rerun operations idempotent across retries and duplicate webhooks.
- Implement explicit state machines for quotes, bookings, payments, disputes, approvals, and jobs.
- Preserve the specified 70/30 release rule, cancellation calculation against the full quote, and applicable 24-hour windows.
- Freeze relevant releases during disputes, recovery cases, and payout locks.
- Pause the applicable payment-window clock automatically during a full processor outage; preserve elapsed time and notify both parties.
- Require two distinct authorized approvers for large refunds and fund-related reruns. Block unclassified actions until the “large” threshold is approved.
- Require human approval for advances and large fund actions. Keep AI payment investigation credentials read-only.
- Enforce the 48-hour post-recovery payout-change lock and hold due payouts until it ends.
- Run timed operations through Trigger.dev; do not depend on an open client or browser timer.

### Privacy and AI

- Collect minimum necessary personal data and record consent purpose and version.
- Restrict dietary/allergy data to the host and assigned caterer; implement approved post-event deletion.
- Support access, export, and deletion workflows while preserving legally required financial records.
- Resolve anonymization and regulatory-retention conflicts before claiming deletion compliance.
- Delete verification documents after verification according to an approved legally reviewed policy; retain only approved audit-chain evidence.
- Require explicit biometric consent, encrypted template storage, and minimal raw-image retention.
- Send sensitive AI inputs only to an owner-approved model provider with a verified ZDR agreement.
- Treat prompts, retrieved content, and model output as untrusted. Enforce authorization outside the model.
- Share protected information only through revocable, audited access grants; never let AI reveal hidden fields.
- Separate marketing consent from transactional messaging; include unsubscribe links and the company postal address in marketing email.

## How to handle ambiguity

- Ask a focused question with the feature ID, competing interpretations, risks, and recommended options.
- Log unanswered questions in `docs/open-questions.md` with owner, impact, blocked work, and decision status.
- Escalate quote date-lock versus concurrent soft-hold semantics, deadline anchors, in-flight payment expiry, team-size interpretation, and no-show visibility boundaries.
- Escalate undefined approval thresholds, custody licensing, verification limits, retention conflicts, and missing provider approvals before implementation.
- Continue only on independent, reversible work; label assumptions and keep blocked behavior unavailable.
- Record explicit owner decisions and update the PRD/architecture before implementing the resolved policy.

## Lovable migration notes
- Pages keep the original react-router-style API through `src/lib/router.tsx` (a thin adapter over TanStack Router), so imported components stay unchanged. Route files live in `src/routes`, and page bodies live in `src/pages`.
- Database changes waiting for the owner's Supabase connection go in `supabase/pending/`. `supabase/tests/run-local.sh` runs them after `supabase/migrations/`, and they move into migrations through the migration tool once Supabase is connected.
- Payments use Paystack. Webhooks arrive at `/api/public/paystack/webhook` and are rejected unless they carry a valid HMAC-SHA512 signature.
