## 3. Backend and server functions

### Trust boundary

Expose `/api/v1` through Edge Functions. TanStack Start server functions may adapt sessions or rendering but must not duplicate domain logic. Clients cannot directly mutate business tables.

Validate Auth0 signature, issuer, audience, expiry, session status and current application membership. Map `sub` uniquely to `users.id`. Every command resolves permissions from current database state.

Execute application transactions under a non-bypass database role with trusted transaction-local identity context. RLS applies even behind the API. Privileged maintenance functions require narrow grants, fixed execution context and audit entries; never use unrestricted service credentials as the normal request path.

### Domain behavior

- **Quotes:** immutable sent revisions; `draft → sent → countered/accepted/declined/expired`. Only vendors author revisions. Sending a revision restarts its 24-hour quote expiry.
- **Calendar:** proposed advisory sent-quote locks and competing accepted-quote holds reconcile conflicting requirements. **Booking rollout remains blocked pending approval.**
- **Race resolution:** serialize allocation by vendor/date/capacity. A unique allocation selects the first confirmed payment processed by the platform, subject to approved ordering rules. Losing successful payments create refund obligations and alternatives.
- **Payments:** maintain double-entry ledger records and partner references. Recognize successful payment only through authenticated partner evidence, not browser return URLs.
- **Release:** allocate 70% for initial vendor release and 30% for completion release. Disputes, recovery locks and compliance holds take precedence. Automatic completion release requires an approved event-end definition.
- **Cancellation:** host cancellation within 24 hours forfeits 20% of full quote value; vendor cancellation creates a full refund and immutable Trust Score deduction.
- **Recovery:** no-show reporting opens a restricted ticket, pauses vendor listing/payouts and offers replacements. The 50% replacement advance requires human approval.
- **Jobs:** transactional outbox records accompany state changes. Trigger.dev executes idempotent expiry, release, verification escalation, renewal, deletion and reminder tasks. A periodic sweeper catches missed timers.
- **Outages:** automatically recorded full payment-outage intervals pause payment windows; recovery recomputes effective deadlines without manual timer edits.
- **Subscriptions:** self-service cancellation, reminders, receipts, retry, grace and downgrade preserve existing bookings.
- **Trust:** deterministic, versioned score calculations; staff cannot override deductions or ranking effects.

Refund promises require recoverable funding: releasing 70% immediately conflicts with later 80% or full refunds unless partner recovery or platform reserves cover the difference. This is a launch gate.

## 6. Integrations and failure handling

**Proposed retry default:** five transient-error attempts with jittered exponential backoff, capped at 15 minutes; respect retry instructions. Alert immediately for critical failures and again on exhaustion. Permanent validation failures do not retry.

| Integration | Failure, retry and fallback |
|---|---|
| Auth0 | Login/MFA outage blocks new privileged sessions; never bypass verification. Cached signing keys remain bounded; unknown keys fail closed. |
| Supabase | Database outage blocks writes; show safe cached UI. Reconnect Realtime with backoff, refetch by cursor; polling fallback is degraded service. |
| Paystack | Timeout creates `unknown`, not `failed`. Reconcile by reference before retrying. Backup processing requires a separately approved integration; never charge another processor while outcome is ambiguous. |
| Banking/payment rails | No wallet custody or transfers before partner authorization. Reconcile ledger against partner statements; unresolved differences freeze affected actions. |
| Trigger.dev | Retry by durable operation key. Database sweeper catches overdue jobs; terminal failures enter operations queue. |
| Resend / messaging / SMS | Always create in-app notice. Retry consented messaging, then email; critical categories also use SMS. Store delivery receipts without sensitive bodies. |
| Algolia | Retry indexing from outbox. Fall back to bounded Postgres public-vendor filtering. Search results never prove availability or authorization. |
| AI model through Vercel AI SDK | Timeouts produce editable partial drafts or structured planning fallback. Switch only to contractually approved providers; never silently downgrade privacy terms. |
| Identity registries | Queue verification; show Unverified and restricted access. Escalate unresolved cases by 24 hours; manual issuer checks require audited access. |
| File scanner | Keep uploads quarantined during outage; no download or AI processing. Scanner selection is open. |
| Sentry | Buffer bounded, scrubbed diagnostics; logging failure must not leak data. Sensitive operations requiring durable audit fail closed if that audit cannot persist. |

## 8. Validation and error handling

Validate types, bounds, ownership, state transitions and capabilities server-side. Money never uses floating-point arithmetic. Reject stale revisions, expired confirmations, duplicate claims and unsupported currencies.

Confirmation tokens bind actor, action, terms, amount and expiry. Financial approvals become invalid if their payload changes.

```json
{"error":{"code":"QUOTE_EXPIRED","message":"Request a revised quote.",
 "request_id":"req1","retryable":false}}
```

Use `400` malformed, `401` unauthenticated, `403` forbidden, concealed `404` for inaccessible objects, `409` conflict, `422` field validation, `429` throttling and `503` dependency outage. Never expose raw partner errors, document identifiers or sensitive fields.

## 9. Performance and caching

## Twelve-Factor baseline

- **Config:** All secrets and environment-specific settings live in environment variables, never in the repository.
- **Backing services:** Database, email, payments and storage are attached by URL or key, so each can be swapped per environment.
- **Build, release, run:** Every deploy is built once, tagged, and can be rolled back to the previous release.
- **Processes:** Servers keep no session state in memory; state lives in the database or the auth provider.
- **Dev/prod parity:** Preview and production use the same services and schema migrations, applied in order.
- **Logs:** Logs are structured events sent to the observability tool, never written only to local files.
- **Admin processes:** Data fixes and backfills run as reviewed, one-off migrations or scripts, not manual edits in production.
