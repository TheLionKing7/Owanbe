### Authoritative workflow rules

- Quotes are immutable revisions: `draft → sent → countered/accepted/declined/expired`. A counter requires a vendor-authored revision; sending that revision restarts its 24-hour expiry.
- **Proposed interpretation requiring approval:** sent quotes create advisory date locks; accepted quotes create competing 24-hour payment holds. This reconciles the feature map’s conflicting lock and race rules. Until approved, booking rollout is blocked.
- **Assumption:** one vendor capacity unit per date initially. A unique allocation constraint and serialized transaction select the first confirmed payment processed by the authoritative allocator. Late successful competing payments create refund obligations, receipts, and alternatives.
- Full processor outages automatically pause payment-window elapsed time through persisted outage intervals. Do not automatically extend unrelated dispute or cancellation deadlines.
- Split confirmed funds 70/30; freeze the held balance on dispute. Release the remainder after explicit completion or the approved silence deadline.
- Host cancellation is allowed within 24 hours of confirmed payment and forfeits 20% of the full quote. Vendor cancellation creates a full-refund obligation and immutable Trust Score deduction.
- Already-released funds require partner-supported recovery or funded reserves. Refund obligations are not presented as completed refunds.
- Recovery locks block payout changes and due payouts for 48 hours.
- Financial side effects use stable operation identifiers; automatic actions execute previously approved policy, never AI instructions.

Persist state changes, balanced ledger entries, audit events, and outbox messages together. Jobs consume outbox records at least once, using unique business-effect keys. Retry transient failures with jittered backoff; permanent failures require intervention.

| Supabase Storage | Keep upload quarantined; retry transfer/scan; no bypass of scanning |

## Twelve-Factor baseline

- **Config:** All secrets and environment-specific settings live in environment variables, never in the repository.
- **Backing services:** Database, email, payments and storage are attached by URL or key, so each can be swapped per environment.
- **Build, release, run:** Every deploy is built once, tagged, and can be rolled back to the previous release.
- **Processes:** Servers keep no session state in memory; state lives in the database or the auth provider.
- **Dev/prod parity:** Preview and production use the same services and schema migrations, applied in order.
- **Logs:** Logs are structured events sent to the observability tool, never written only to local files.
- **Admin processes:** Data fixes and backfills run as reviewed, one-off migrations or scripts, not manual edits in production.
